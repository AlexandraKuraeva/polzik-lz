## Context

Учётки сотрудников живут в своей таблице `public.users`, а вход делает next-auth (Credentials). Supabase Auth
не используется. У таблицы две дыры, которые встроенная авторизация закрыла бы сама:

1. **Email не уникален.** Ограничения в базе нет, есть только проверка «есть ли такой email» перед вставкой
   в `actionCreateUser` и `ensureAdmin`. Она не атомарна: двойной клик, два админа одновременно, вставка через
   Studio или импорт дампа дают дубль. Дубль ломает вход обоим: `fetchUserByEmail` (`.maybeSingle()`) получает
   `PGRST116` и возвращает `null`, то есть «пользователь не найден». `getUser` (`.single()`) роняет главную.
   `ensureAdmin` при дубле решает, что админа нет, и создаёт ещё одного на каждом старте.
2. **Пароли хранятся открытым текстом** и сравниваются `!==` в `auth.config.js`. Любой дамп, бэкап или
   доступ к Studio раскрывает пароли всех сотрудников.

Цель: довести свою таблицу до нормы, не меняя архитектуру входа.

**Решения пользователя (2026-10-20):**

- Остаёмся на своей таблице и next-auth, на Supabase Auth не переходим. Почему: Docker-стенд сознательно
  минимальный (Postgres + PostgREST), для Supabase Auth понадобились бы GoTrue и шлюз, а также переписанный
  вход, сессии и middleware. Для внутреннего сервиса на два десятка человек это лишнее.
- Приёмка: Саша Кураева на локалке (не Саша Любаков — их двое, не путать). Она же реализует план.
- Облачный Supabase + Vercel живые: Саша Кураева разворачивает проект у себя на облачной базе. Значит,
  миграция обязана работать и там. Применяет её Саша Кураева в SQL Editor своего проекта, сессии к облаку
  доступа нет.

**Решения планирования:**

- **Уникальность по `lower(email)`**: уникальный индекс `users_email_lower_key ON public.users (lower(email))`
  плюс нормализация email (`trim` + нижний регистр) в коде на входе, при создании и при поиске. Почему:
  индекс по выражению ловит и `Admin@x` против `admin@x`, даже если вставка прошла мимо кода (Studio, дамп).
- **Гонку закрывает база, а не проверка в коде.** Вставка, упавшая с `23505` (unique_violation), значит
  «email занят». В `actionCreateUser` это ошибка поля `email`, в `ensureAdmin` — «админ уже есть». Проверка
  до вставки остаётся ради понятного сообщения в обычном случае.
- **bcrypt через `bcryptjs`**, cost 10. Почему `bcryptjs`: чистый JS, без нативной сборки под alpine в
  Dockerfile и на Vercel. Почему bcrypt: существующие пароли можно захешировать прямо в SQL через pgcrypto
  (`extensions.crypt(password, extensions.gen_salt('bf', 10))`), и `bcryptjs.compare` такие хеши (`$2a$`)
  принимает.
- **Миграция данных живёт в `supabase/db/polziks-schema.sql` и идемпотентна**: нормализация email, проверка
  дублей, индекс, хеширование только строк, где пароль ещё не bcrypt (`!~ '^\$2[aby]\$'`). Один файл на все
  базы: Docker прогоняет его при инициализации и в каждом `vps-update.sh`, облако — руками в SQL Editor.
- **Дубли при миграции — громкая ошибка, а не тихий пропуск.** Блок `DO` перед созданием индекса ищет дубли
  `lower(trim(email))` и делает `RAISE EXCEPTION` со списком адресов. Почему: тихий пропуск оставил бы дыру
  незаметной. Разбор дублей — человек.
- **Переходный вход по открытому паролю с перехешированием.** Если в `users.password` не bcrypt-хеш, вход
  сравнивает как раньше и при успехе сразу записывает bcrypt-хеш. Почему: облако обновляется в два шага
  (деплой Vercel, потом SQL руками), и в любом порядке, кроме «сначала код», все остались бы без входа.
  Переходный код делает порядок безопасным для нового кода и дампа с открытыми паролями.
- **Хеширование в одном месте — `createUser` в `data.js`.** Почему: так его получают и форма, и `ensureAdmin`,
  и будущие вызовы, и нельзя забыть.
- **`createUser` возвращает только `PUBLIC_USER_FIELDS`.** Сейчас `.select()` отдаёт всю строку, а
  `actionCreateUser` возвращает её в браузер вместе с паролем (сейчас открытым, после плана — с хешем).
- **`import-dump.sh` после дампа прогоняет и `polziks-schema.sql`**, не только `polziks-access.sql`. Почему:
  дамп из облака до миграции несёт открытые пароли; хешируем сразу, а не при следующем `vps-update.sh`.

**Отвергнутые варианты:**

- Supabase Auth (`auth.users` + `public.profiles`) → см. первое решение: тяжелее стенд и переписывание входа.
- Простой `UNIQUE (email)` без `lower` → регистр в обход кода снова даёт логический дубль.
- Upsert `on_conflict=email` через PostgREST → не работает с индексом по выражению; ловить `23505` проще.
- Нативный `bcrypt` / `argon2` → нативная сборка под alpine и Vercel; выигрыша для двух десятков учёток нет.
- `scrypt` из `node:crypto` (без зависимостей) → существующие пароли тогда хешировать только из Node
  скриптом; pgcrypto bcrypt позволяет сделать это одной SQL-командой во всех базах.
- Хешировать без переходного входа → требует строгого порядка «код, затем SQL» в облаке, ошибка порядка
  выключает вход всем.
- Пропускать индекс при дублях с предупреждением → дыра остаётся, а предупреждение в выводе `vps-update.sh`
  никто не прочтёт.

**Что проверено заранее (2026-10-20):**

- Docker-база `polziks` (локальный стенд с дампом): 19 сотрудников, дублей `lower(trim(email))` нет, все email
  уже в нижнем регистре, пароли все открытым текстом, пустых нет.
- pgcrypto установлен в схеме `extensions`; `extensions.crypt('x', extensions.gen_salt('bf', 10))` даёт `$2a$10$…`.
- Облачная база не проверялась: доступа нет. Дубли там возможны — это ловит блок `DO` с ошибкой.
- `vps-update.sh` прогоняет `polziks-schema.sql` и `polziks-access.sql` одним `psql` с `ON_ERROR_STOP=1` от
  `supabase_admin`, после `docker compose up -d --build` — то есть новый код уже работает, когда идёт SQL.
- `import-dump.sh` после дампа прогоняет только `polziks-access.sql`.
- Пароль сравнивается в `auth.config.js` (`password !== user.password`); `createUser` в `data.js` вставляет
  пароль как есть и возвращает `.select()` всей строки; `actionCreateUser` отдаёт её клиенту.
- `validateFormCreateUser` требует пароль от 6 символов; email не нормализуется нигде.
- Тестов и `typecheck` в проекте нет; есть `npm run lint` и `npm run build`. В WSL-копии нет `node_modules`.
- Смены пароля в интерфейсе нет.

## ТЗ по фазам

### Фаза 1 — Уникальный email

- **Для кого и зачем:** для админа и сотрудников. Два аккаунта с одной почтой больше невозможны ни через
  форму, ни в обход неё, а значит, никто не теряет вход из-за дубля.
- **Готово, когда:**
  - `polziks-schema.sql` нормализует email, проверяет дубли и создаёт `users_email_lower_key`; повторный
    прогон проходит без ошибок и изменений;
  - при подложенном дубле прогон падает с сообщением, где перечислены адреса;
  - email нормализуется при входе, при создании (форма и `ensureAdmin`) и в `fetchUserByEmail`;
  - вторая вставка того же email (в любом регистре) даёт в форме ошибку поля «Email уже занят», а
    `ensureAdmin` молча считает админа существующим;
  - `fetchUserByEmail` при нескольких строках бросает ошибку с понятным текстом в логе, а не возвращает `null`.
  - Доказательство: тестовый стенд `polziks-test` (см. Verification), два прогона схемы, `psql` с двойной
    вставкой, вход в разном регистре через `curl`.
- **Что прочитать до правок:** `supabase/db/polziks-schema.sql`, `app/lib/data.js` (`fetchUserByEmail`,
  `getUser`, `createUser`), `app/lib/actions.js` (`actionCreateUser`), `app/lib/ensure-admin.js`,
  `auth.config.js`, `app/lib/utils.js`, `scripts/vps-update.sh`, `docker-compose.yml` (как монтируется схема).
- **Решения:** из Context — индекс по `lower(email)`, `23505` как «занято», громкая ошибка при дублях, нормализация
  `trim` + нижний регистр. Порядок в SQL: нормализация → `DO`-проверка → `CREATE UNIQUE INDEX IF NOT EXISTS`.
- **Не в скоупе фазы:** пароли (Ф2), `getUser` и прочие функции `data.js`, где не проверяется `error`, если
  их не касается email.
- **Коммит:** «Уникальный email сотрудника: индекс в базе и нормализация».

### Фаза 2 — Хеши паролей

- **Для кого и зачем:** для всех сотрудников. Пароли не лежат в базе, дампах и бэкапах открытым текстом;
  вход у всех продолжает работать без смены паролей.
- **Готово, когда:**
  - новый пользователь (форма и `ensureAdmin`) сохраняется с bcrypt-хешем;
  - вход по bcrypt-хешу работает, по неверному паролю — нет;
  - вход пользователя с открытым паролем работает и после него в базе лежит хеш;
  - `polziks-schema.sql` хеширует все не-bcrypt пароли, повторный прогон ничего не меняет;
  - `import-dump.sh` после дампа прогоняет и схему, и права;
  - `actionCreateUser` не возвращает поле `password`.
  - Доказательство: тестовый стенд `polziks-test`, `psql`-выборка `password ~ '^\$2'` до и после, вход через
    `curl` для трёх случаев, загрузка дампа с открытыми паролями.
- **Что прочитать до правок:** `auth.config.js`, `auth.js`, `middleware.js` (импортирует конфиг auth),
  `app/lib/data.js`, `app/lib/actions.js`, `app/lib/ensure-admin.js`, `supabase/db/polziks-schema.sql`,
  `scripts/import-dump.sh`, `Dockerfile`, `package.json`.
- **Решения:** из Context — `bcryptjs` cost 10, хеширование в `createUser`, переходный вход с перехешированием
  (новая функция записи пароля в `data.js`), SQL-хеширование через `extensions.crypt`, `PUBLIC_USER_FIELDS`
  в ответе `createUser`. Хеширование в схеме — после блока email из Ф1.
- **Не в скоупе фазы:** смена и сброс пароля, удаление переходного входа, политика сложности паролей.
- **Коммит:** «Пароли сотрудников хранятся bcrypt-хешем».

## Сквозное (все фазы)

- `polziks-schema.sql` идемпотентен целиком: любое число прогонов на любой базе (пустая, с дампом, уже
  мигрированная) даёт тот же результат.
- Пароль, открытый или хеш, не уходит в браузер и не пишется в лог.
- Сообщения пользователю — на русском, ошибки форм — `{ message, errors: { field }, data }`.
- Проверка на Docker — только отдельным проектом `polziks-test` со своими портами и env-файлом вне проекта;
  стенд `polziks` пользователя и его `.env` не трогать. После проверки — `down -v`.
- Новых npm-зависимостей, кроме `bcryptjs`, нет.

## Риски

- **Дубли в облачной базе.** Схема упадёт на `DO`-проверке, индекс не создастся. Ловим громкой ошибкой со
  списком; разбирает Саша Кураева по `DEPLOY.md`.
- **Порядок в облаке.** Старый код + захешированная база = никто не войдёт. Закрыто переходным входом только для
  нового кода, поэтому в документации и подготовке: сначала деплой, потом SQL.
- **`vps-update.sh` падает на схеме** → `polziks-access.sql` в этом прогоне не применится (тот же `psql`,
  `ON_ERROR_STOP`). Права уже стоят с прошлых прогонов, сервис работает; после разбора дублей — повторить.
- **`bcryptjs` попадает в бандл middleware** (через `auth.config.js`). Чистый JS, edge его тянет; проверяется
  `npm run build` и входом на стенде.
- **Хеширование необратимо.** Открытые пароли после миграции не прочитать — ни для выдачи сотрудникам, ни для
  отката. Ловим выгрузкой `users` перед миграцией (Ф3 документирует) и сбросом пароля SQL-запросом.
- **Переходный вход оставляет путь сравнения открытым текстом.** После миграции всех баз он мёртвый код;
  убрать отдельным ТЗ.

## Verification

Стенд: `docker compose -p polziks-test --env-file <env в scratchpad> up -d --build` с портами 3100/54400
(образец env — `.env.example` через `generate-env.mjs`), дамп — тот, что лежит в `scripts/` у проверяющего, если
есть, иначе созданные руками пользователи с открытыми паролями.

1. **Миграция на данных с открытыми паролями.** Загрузить дамп в `polziks-test`: `import-dump.sh` вызывает
   `docker compose` без флагов, поэтому проект и env задать окружением (`COMPOSE_PROJECT_NAME=polziks-test`,
   `COMPOSE_ENV_FILES=<env>`), либо вставить пользователей через `psql`. После — все `password` вида `$2…`,
   индекс `users_email_lower_key` есть. Второй прогон `polziks-schema.sql` — без ошибок, `UPDATE 0`.
2. **Вход.** Сотрудник из дампа входит своим старым паролем. Неверный пароль — «неверные данные». Email в
   другом регистре (`Admin@LZ.media`) — входит.
3. **Переходный вход.** Вручную вернуть одному пользователю открытый пароль, войти, проверить, что в базе снова
   хеш.
4. **Создание сотрудника.** Форма «Сотрудники» → новый сотрудник → в базе хеш, в ответе action нет `password`.
   Тот же email в другом регистре → ошибка поля «Email уже занят».
5. **Дубль в обход кода.** `insert` второй строки с тем же email в `psql` → ошибка `23505`.
6. **Дубль до индекса.** На пустом стенде удалить индекс, вставить дубль, прогнать схему → ошибка со списком
   адресов.
7. **Админ из `.env`.** Перезапуск сервиса при существующем админе — новой строки нет, ошибок в логе нет.
8. `npm run lint` и `npm run build` проходят.

Риск смотреть в коде: все места, где email попадает в запрос, нормализуют его одинаково; ни один `select`
пользователя, уходящий наружу, не включает `password`.
